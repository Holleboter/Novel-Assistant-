# 小说助手智能体项目规划报告书

## 1. 项目概述

本项目拟建设一个面向长篇小说创作的智能体系统。系统根据用户输入的题材、风格、主角设定、目标读者、爽点方向和内容约束，自动生成小说蓝图，并在用户确认后持续生产章节内容。章节生成后，系统会执行内容质检、连续性检查、伏笔检查和自动修订，最终形成可持续迭代的小说生产流程。

项目核心目标不是做一个简单的文本生成工具，而是建设一套具备长期记忆、图谱理解、流程编排和质量闭环的小说创作系统。

## 2. 建设目标

### 2.1 总体目标

构建一个可以从创意输入到章节产出的自动化小说助手智能体，覆盖小说构思、人物设计、世界观生成、主线规划、章节写作、内容质检、自动修订和状态沉淀。

### 2.2 阶段目标

第一阶段完成最小可用闭环：

- 用户输入小说需求。
- 系统生成小说基础蓝图。
- 系统生成主角、关键配角、主要势力、核心矛盾和世界规则。
- 系统将人物关系和小说蓝图写入 Neo4j。
- 系统生成章节大纲。
- 系统生成单章正文。
- 系统对章节进行质检并输出修改建议。
- 系统根据质检结果修订章节。
- 系统更新人物状态、事件进展、伏笔状态和章节摘要。

第二阶段增强创作控制能力：

- 支持用户人工确认或修改蓝图。
- 支持人物关系图谱可视化。
- 支持小说发展路线图可视化。
- 支持按章节追踪伏笔埋设与回收。
- 支持多轮章节连续生成。
- 支持风格约束、题材规则和平台规则。

第三阶段建设完整创作工作台：

- 提供 Web 管理界面。
- 支持多小说项目管理。
- 支持章节审阅、重写、导出。
- 支持图谱编辑后反向影响后续生成。
- 支持模型配置、任务日志和质量分析。

## 3. 核心设计原则

### 3.1 先规划，后写作

系统不能直接根据一句话开始写正文。每次生成章节前，应先明确本章目标、关键事件、人物状态、冲突推进、伏笔动作和禁止事项。

### 3.2 事实源优先

长篇小说的稳定性依赖事实源，而不是依赖长上下文硬塞。人物信息、世界规则、事件历史、伏笔状态和章节摘要都应持久化存储，并在写作前按需检索。

### 3.3 图谱参与生成

人物关系和小说蓝图不只用于展示，也应参与生成和质检。系统在写作前检索相关人物、关系、事件和伏笔；在写作后根据正文更新图谱。

### 3.4 质检闭环

章节生成不是终点。每章必须经过质量检查，检查内容包括人设一致性、剧情连续性、世界观规则、伏笔推进、节奏问题、AI 味、重复表达和大纲偏离。

### 3.5 可回滚、可追踪

每次生成、修订和状态更新都应保留记录。系统需要支持查看某章使用了哪些上下文、触发了哪些规则、更新了哪些图谱节点。

## 4. 技术路线

### 4.1 技术栈建议

- 语言：Python
- 智能体流程编排：LangGraph
- 数据校验：Pydantic
- 图数据库：Neo4j
- 关系型/轻量状态：SQLite 或 PostgreSQL
- 向量检索：Milvus 或其他向量数据库
- 后端服务：FastAPI
- 前端可视化：React + React Flow 或 Cytoscape.js
- 配置管理：`.env` + 项目级配置文件

当前本地 Docker 中已有可用的 Neo4j：

- Browser: `http://localhost:7474`
- Bolt: `bolt://localhost:7687`
- User: `neo4j`
- Password: use your local `.env` value

### 4.2 LangGraph 定位

LangGraph 用于管理智能体执行流程，而不是直接承担知识图谱职责。它负责控制不同节点的执行顺序、状态传递、人工确认、失败重试和流程回滚。

建议第一版 LangGraph 流程如下：

```text
用户需求输入
  -> 需求分析节点
  -> 小说蓝图节点
  -> 人物设定节点
  -> 世界观设定节点
  -> 图谱写入节点
  -> 大纲规划节点
  -> 人工确认节点
  -> 章节计划节点
  -> 章节写作节点
  -> 章节质检节点
  -> 自动修订节点
  -> 图谱与状态更新节点
```

### 4.3 Neo4j 定位

Neo4j 用于保存小说知识图谱。第一版重点保存人物、关系、事件、章节、伏笔、势力和世界规则。

建议基础节点类型：

```text
Novel
Character
Faction
Location
WorldRule
Arc
Chapter
Event
Hook
Theme
```

建议基础关系类型：

```text
(:Novel)-[:HAS_CHARACTER]->(:Character)
(:Novel)-[:HAS_ARC]->(:Arc)
(:Novel)-[:HAS_WORLD_RULE]->(:WorldRule)
(:Character)-[:ALLY_OF]->(:Character)
(:Character)-[:ENEMY_OF]->(:Character)
(:Character)-[:MENTOR_OF]->(:Character)
(:Character)-[:BELONGS_TO]->(:Faction)
(:Character)-[:LOCATED_AT]->(:Location)
(:Arc)-[:HAS_CHAPTER]->(:Chapter)
(:Chapter)-[:CONTAINS_EVENT]->(:Event)
(:Event)-[:INVOLVES]->(:Character)
(:Event)-[:ADVANCES_HOOK]->(:Hook)
(:Hook)-[:PLANTED_IN]->(:Chapter)
(:Hook)-[:RESOLVED_IN]->(:Chapter)
```

## 5. 系统模块规划

### 5.1 需求理解模块

负责解析用户的创作需求，抽取题材、风格、主角方向、核心冲突、目标章节数、单章字数、读者期待和禁忌内容。

输出：

- 创作需求摘要
- 缺失信息列表
- 初步创作方向
- 用户确认问题

### 5.2 小说蓝图模块

负责生成小说基础方案。

输出：

- 小说标题候选
- 核心卖点
- 题材类型
- 世界观概述
- 主线矛盾
- 主角成长路线
- 阶段性剧情路线
- 结局方向

### 5.3 人物设定模块

负责生成主角、关键配角、反派和势力人物。

输出：

- 人物基础信息
- 人物目标
- 人物弱点
- 人物关系
- 人物成长线
- 人物当前状态

### 5.4 图谱管理模块

负责将小说蓝图、人物关系和章节事件写入 Neo4j，并提供查询能力。

核心能力：

- 创建小说图谱
- 更新人物关系
- 查询人物邻居节点
- 查询伏笔状态
- 查询某章节影响的人物和事件
- 输出前端可视化数据

### 5.5 大纲规划模块

负责将小说蓝图拆成卷纲、阶段目标和章节大纲。

输出：

- 卷级大纲
- 阶段冲突
- 章节列表
- 每章目标
- 每章必须推进的事件
- 每章禁止偏离的内容

### 5.6 章节写作模块

负责根据章节计划和图谱上下文生成正文。

输入：

- 小说蓝图
- 本章目标
- 相关人物关系
- 相关历史事件
- 当前伏笔状态
- 前文摘要
- 风格要求

输出：

- 章节标题
- 章节正文
- 写作自检说明
- 本章新增事实候选

### 5.7 内容质检模块

负责检查章节是否满足创作要求。

检查维度：

- 人设一致性
- 世界观一致性
- 人物关系一致性
- 事件因果是否成立
- 伏笔是否合理推进
- 是否偏离大纲
- 节奏是否拖沓
- 表达是否重复
- 语句是否流程清晰
- 是否存在明显 AI 味
- 是否存在敏感或违禁内容

输出：

- 质检得分
- 问题列表
- 严重程度
- 修改建议
- 是否需要自动修订

### 5.8 自动修订模块

负责根据质检报告修订章节内容。

修订模式：

- 局部修复
- 润色增强
- 节奏压缩
- 情节重写
- 去 AI 味改写

### 5.9 状态更新模块

负责从最终章节中抽取事实，并更新图谱和长期状态。

更新内容：

- 人物状态变化
- 人物关系变化
- 新事件
- 新伏笔
- 已推进伏笔
- 已回收伏笔
- 地点变化
- 章节摘要

## 9. 风险与应对

### 9.1 长篇连续性失控

风险：章节越多，人物状态和伏笔越容易混乱。

应对：

- 使用 Neo4j 保存关系。
- 使用章节摘要降低上下文负担。
- 写作前只检索相关上下文。
- 写作后强制更新状态。

### 9.2 LLM 输出结构不稳定

风险：模型可能输出不合法 JSON 或遗漏字段。

应对：

- 使用 Pydantic 校验。
- 对失败输出进行重试。
- 对关键状态更新使用 delta 模式。
- 不允许模型直接覆盖全量图谱。

### 9.3 图谱过度复杂

风险：一开始设计过大，导致项目推进缓慢。

应对：

- 第一版只做人物、章节、事件、伏笔。
- 地点、势力、世界规则作为第二优先级。
- 图谱展示先输出 JSON，再做前端。

### 9.4 质检标准模糊

风险：质检报告流于形式。

应对：

- 将质检维度结构化。
- 每个问题必须给出证据和修改建议。
- 严重问题阻断自动通过。

### 9.5 与现有开源项目的许可证边界

风险：直接复制 AGPL 项目代码会影响后续发布和商业化。

应对：

- 只借鉴架构思想。
- 独立实现代码。
- 不复制 InkOS 源码、提示词和文件结构。

## 11. 验收标准

第一版完成后，应满足以下标准：

- 用户输入一个小说创意，系统能生成结构化小说蓝图。
- 系统能将主角、配角、反派和势力关系写入 Neo4j。
- 系统能导出人物关系图谱数据。
- 系统能根据蓝图生成至少一章小说正文。
- 系统能对章节进行质检并输出明确问题。
- 系统能根据质检报告自动修订章节。
- 系统能将最终章节产生的新事件和伏笔写回图谱。

## 12. 推荐执行顺序

建议接下来按以下顺序推进：

1. 建立 Python 项目骨架。
2. 接入 Neo4j 并封装图谱仓储层。
3. 定义小说、人物、章节、事件、伏笔的 Pydantic 模型。
4. 建立 LangGraph 最小工作流。
5. 实现小说蓝图生成节点。
6. 实现人物关系写入节点。
7. 实现章节计划和章节生成节点。
8. 实现质检和修订节点。
9. 实现图谱查询和可视化数据导出。

## 13. 总结

本项目应定位为具备长期创作能力的小说智能体，而不是单次文本生成器。LangGraph 负责编排创作流程，Neo4j 负责保存和检索小说知识图谱，Pydantic 负责保障结构稳定，LLM 负责创意生成和文本生产。

第一版的关键不是功能多，而是跑通一个可靠闭环：从用户创意到小说蓝图，从蓝图到人物关系图谱，从图谱到章节生成，再从章节回写图谱。只要这个闭环跑通，后续 Web 工作台、批量生成、多小说管理和复杂质检都可以自然扩展。
